# 广州地铁 · 运行推演

把几个开源广州地铁项目合并成的一个单页工具：在线路示意图上按运行图推演列车位置，并算每个站下一班还有多久。

线上地址：

- Cloudflare Pages（含共享校正）：https://gzmetro-live-0914.pages.dev/
- GitHub Pages（纯静态）：https://XiaoChess0914.github.io/gzmetro/

> 不是实时车辆定位。广州地铁没有公开的车辆位置 / GTFS-RT 接口，官方“列车到站查询”只在微信小程序里试点过计划到站，接口也已封禁。这里只能按公开首末班、发车间隔和区间运行时分推演。

## 运行

```sh
cd /storage/emulated/0/gzmetro_app
node server.mjs
```

打开 http://127.0.0.1:3456

## 功能

- 28 条线（地铁 + 有轨 + 广佛/佛山线路），横向线路条切换
- 线路示意图：线路几何、换乘站、站名避让、滚轮/双指缩放、拖动
- 列车位置：按站间几何距离 + 计划运行时分生成速度曲线（出站加速、区间中段最快、进站减速），位置由曲线推进；白色圆点带脉冲，标记前小三角指向行车方向，tooltip 显示区间推算 km/h（18、22 号线标称最高 160 km/h，页面 km/h 是区间反推峰值，不是车辆最高速度）；快车为橙色方块“快”
- 停站：中间站停留约 20–25 秒，起点站待发约 1 分 36 秒；停站时列车钉在站上；快车只在停靠站停，跳停站直接通过
- 站台屏：站点名下方把上下行合并，按时间显示最近 3 班的方向、快车标记、倒计时和到站/始发钟点；起点站待发标“始发”，终点站到达标“已到站”；方向卡片另列上/下行各未来 3 班，含“还有几站”
- 站点倒计时：快车单独标“快”，跳停站不显示快车；终点站到达显示“已到站”，起点站待发显示“始发”
- 首末班前后：站台首班是列车到达本站的时间，地图同时显示已从终点站发出的车；末班后本站无车，但线上可能还有车在跑完区间
- 快车：18 / 14 / 21 号线按公开快车时刻表生成，14 号线条用 2026 年 3 月起增停竹料的 13 站方案，21 号线条为天河公园短交路
- 实际校正：可按站台屏“往 X 方向还有 N 分钟”修正当前线路当前方向今天的全部班次；0 表示已到站；配置共享服务后，提交的校正会在 45 分钟内按中位数同步给其他访客，未配置时只存本机
- 站点下拉、上一站/下一站、点击地图站点切换
- 1× / 60× / 300× 加速演示（再点回到 1×）
- 深色响应式布局，手机上下分栏；左上角为广州地铁完整标志（仅用于识别，与官方无关）

## 实际校正

右侧“实际校正”是对运行图推演的一次人工观测修正，不是实时定位。

1. 在站台屏看到“往 X 方向 还有 N 分钟”。
2. 选同一方向，填 N（0 = 已经到站）；如果这班是快车，勾选“快车”。
3. 程序取模型里下一班到站的预计时间，把这班对齐到 N，并把该类型今天这班及之后的发车时刻整体平移；该站倒计时从这班开始，到站早于这班的同类型列车会从地图上隐去。这里按“到站时间”而不是“发车时间”裁，发车早但到站晚的慢车仍会保留。快车和普通车分开校正：本地键、共享上报键都带 `|E` 后缀，互不覆盖。

### 本机模式

没有配置共享服务时，校正只存 localStorage（键 `gzmetro.calib.v1`），只影响当前线路、当前方向、当天，换线或第二天自动失效。重复校正会叠加：每次都基于当前已平移后的模型再对齐。

### 共享模式

在 `sync-config.js` 里填上 Cloudflare Pages 的 `/api` 地址后，点“重算”会把“线路 / 方向 / 站号 / 无校准的预计分钟 / 实际分钟”提交到后端；后端取最近 45 分钟内同一线路、同一方向的校正中位数，作为所有访客共用的平移量。页面每 30 秒刷新一次共享校正，页面隐藏时暂停。

共享校正成功时，本机对同方向的校正会被清掉，避免两套偏移叠加；共享服务连不上时，如果已有共享记录就继续用共享记录，没有就退回本机校正。清除按钮只清本机记录，不会删除别人已经提交的数据。

后端是 Cloudflare Pages Functions（`_worker.js`）+ D1，和前端在同一个 `pages.dev` 域名下，走 `/api/*`。它只保存校正所需的字段，IP 只存哈希；同一 IP 一分钟最多 3 条。  
校正不能还原区间里的逐段晚点，也不能代替实时车辆位置。

## 部署

### GitHub Pages（纯静态）

把仓库根目录的这些文件放好：

`index.html`、`style.css`、`app.js`、`data.json`、`express.json`、`logo-full.png`、`sync-config.js`、`sync.js`、`_worker.js`

其中 `_worker.js` 只在 Cloudflare Pages 下生效，GitHub Pages 会把它当普通文件忽略。

Settings → Pages → Deploy from a branch → `main` / `(root)` → Save。等 1–2 分钟，访问 `https://<用户名>.github.io/<仓库名>/`。

### Cloudflare Pages + D1（共享校正）

1. 在 Cloudflare 建 D1 数据库，名 `gzmetro-sync`，在控制台执行 `schema.sql`。
2. 用 Git 集成创建 Pages 项目，仓库指向本仓库；构建命令 `exit 0`，构建输出目录 `/`，根目录 `/`。
3. 在 Pages 项目 **设置 → 绑定** 添加 D1 数据库：变量名 `DB`，数据库 `gzmetro-sync`。
4. 在 **设置 → 变量和密钥** 添加密钥 `IP_SALT`，值用一段随机字符串。
5. 重新部署一次，让绑定生效；访问 `https://<项目>.pages.dev/api/health` 应返回 `{"ok":true,...}`。
6. 把 `sync-config.js` 里的 `url` 改成 `https://<项目>.pages.dev/api`，提交并等 Pages 重新部署。

不要用 `workers.dev` 作为共享后端：国内网络下该域名可能被污染，请求会超时。Pages Functions 和前端同域，走 `/api` 更稳。

## 已知误差

- 快车按公开时刻表还原，临时增停/取消、实际越行待避不反映；18 号线工作日与周末暂用同一套快车班次
- 三号线贯通机场北、部分交路未单独建模
- 十一号线首末班与间隔为估算值
- 临时加开、晚点、故障、封站不反映
- 速度是按站间距离和计划运行时分反推的，不是实测速度；区间内用平滑变速曲线，不还原真实牵引/制动；18、22 号线官方标称最高 160 km/h，页面显示的区间峰值通常低于 160
- 实际校正只做“从观测到的下一班起”的时间平移，不能还原区间内的逐段晚点；站点观测误差会带到整条线
- 快车校正只影响快车，不会改动同方向普通车；快车和普通车的本机记录、共享上报键（`|E` 后缀）分开
- 共享校正是 45 分钟内所有提交的中位数，可能被错误观测拉偏；页面最多延迟约 30 秒才看到别人的新提交
- 校正后，到站早于观测班次的同方向列车会从地图上隐去，线上列车数可能比校正前少；发车早但到站晚的慢车不会被误删
- 首末班数据版本：2026-11-03

仅作可视化演示，不用于出行决策。
